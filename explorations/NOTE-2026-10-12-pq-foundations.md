# NOTE — Post-quantum foundations for the DTG ZKP specification: what breaks, what holds, what to change

- **Date:** 2026-10-12
- **Status:** draft review note — local, unpushed; circulation = Mitch (co-chair, ZKP TF; maintainer, DTG WG)
- **Question asked:** the ZKP trust-over-IP spec should be built on post-quantum (PQ) signatures, and Groth16 should not be used because it is not PQ. Review the spec as it stands and say what follows.
- **Verdict (one paragraph):** the spec's *shape* is already PQ-compatible — hash commitments, Merkle roots, Poseidon nullifiers and transcript digests carry the privacy claims, and none of those falls to a quantum adversary. Three layers do fall: (1) the **credential and attestation signatures** (eddsa-jcs-2022 / Ed25519 everywhere in the credential specification; Σ-PS over BLS12-381 in the PCS blind-signature route of records 023/024), (2) the **holder-key material** the records bind to (Baby Jubjub / Ed25519 keys, Pedersen- or KZG-style commitments), and (3) the **proof system** (Groth16/BN254 in the lab; the Groth16 wrapper in ProveKit). The 8 September call already named the order of urgency: the signature is the non-swappable choice, the proof system is swappable by software update. The recommendation is therefore not "swap Groth16 for a STARK" but **"fix the issuance contract first"**: PQ or hybrid signatures over hash commitments (ML-DSA / SLH-DSA on the root or the leaf commitment, never a curve signature inside the circuit), hash-derived holder binding, and a proof-system entry that declares PQ soundness separately from PQ zero-knowledge. Groth16 can remain what the stack file already says it is — a benchmarking vehicle — but a record's **selected** construction for a conformant profile should be a hash-based prover, and the spec should say so where it currently says "a profile trade".
- **Register discipline:** no claim here that any construction is broken today. Every statement is about which assumption each layer rests on and what a cryptographically relevant quantum computer (CRQC) does to that assumption. Dates for CRQC arrival are not asserted; the regulatory horizons quoted in §5 are the ones deployments will be held to regardless.
- **Prior positions this note builds on (do not re-litigate):** liveness requirements v0.4 §9.9 LIV-ALG-01..08 (agility mandatory, PQ migration readiness, continuity does not restore broken guarantees); decision doc §24 ("MUST NOT make post-quantum support a blocker for the first implementable release") and §29 (PQ migration = layer separability + evidence); exploration O8 (layer-separability table, 2026-08); spec Security Considerations item 8 (post-quantum horizon); the 8 Sept call (Sanjam Garg, Denys, Erkan: signature scheme is the critical, non-swappable choice — "a PQ proof system does not mask a pre-quantum signature"); VTI spec VTI-KEY-103..105 (hybrid Ed25519 + ML-DSA-44 attestation proof sets, already normative in a sibling DTG spec).

**Reading the table.** Of the three sibling DTG specifications, two already carry PQ text — the Trust Tasks framework pins ML-DSA-44 and SLH-DSA-128 suites (row O) and the VTI specification defines hybrid Ed25519 + ML-DSA-44 proof sets (row N) — and the credential specification carries none (row F). The ZKP spec's issuance contract therefore has a PQ-capable transport and a PQ-capable identifier layer beneath it, and a classical-only credential layer in between. Rows A–D are the gadget layer the spec's privacy claims actually rest on; they are already PQ. Rows F, G, N are the *issuance* layer and they decide whether the graph is trustworthy at all after a CRQC — this is the layer the 8 September call called non-swappable. Rows I–M are the proof-system layer, swappable per LIV-ALG-01. Row E sits in both: its relation is hash-shaped, its issuance line lets a curve key in.

## 2. What a CRQC does to each layer — soundness is not privacy

The question "is Groth16 broken post-quantum" has two answers and the spec should state both, because they drive opposite deployment decisions.

**2.1 Groth16: soundness falls, zero-knowledge does not.** Groth16 is *perfectly* zero-knowledge: the simulator produces proofs identically distributed to real ones without the witness, with no computational assumption. A proof harvested today therefore leaks nothing about the witness to a future quantum adversary — the "harvest now, decrypt later" threat does **not** apply to the proofs themselves. What falls is *knowledge soundness*, which rests on q-type assumptions in pairing groups that Shor's algorithm breaks: an adversary with a CRQC recovers the trapdoor τ from the public parameters (the setup's "toxic waste" is one discrete logarithm away from the proving key) and forges proofs for false statements. Consequences: (i) no retroactive privacy loss; (ii) **no retroactive soundness loss either** — a proof verified and acted upon before the break was sound at the time; (iii) every verifier that still accepts Groth16 after the break accepts forgeries. The migration trigger is therefore a *verifier-policy* event (retire the suite — VTI-KEY-013's "retire an algorithm without a software change" is the right shape), not an archival one.

**2.2 KZG / Pedersen / Σ-PS: binding falls, hiding holds.** The same split for the pairing- and DL-based commitments the spec names as options (001 KZG accumulator; the blackbox route's hiding KZG; Pedersen in the "SNARK-native commitment" aside of record 022): perfectly hiding, computationally binding. Hidden values stay hidden; openings become forgeable. For the PCS route (row G) this means a quantum vetter can open its credential to any tag — the once-per-tick counting that record 024 exists to provide stops holding.

**2.3 Signatures: unforgeability falls, and that is the whole problem.** Ed25519, ECDSA, BLS, PS and SPS signatures all rest on discrete logarithms. After a CRQC anyone can mint a VMC, a VRC, a VDC or a VAC under any issuer's key; every `signature-verify` clause in every record is satisfied by a forged witness; and because the proof is zero-knowledge the verifier cannot tell a forged credential from a real one. **This is where "a PQ proof system does not mask a pre-quantum signature" bites**: a Flock proof over a forged Ed25519 credential is a perfectly sound proof of a false fact about the world.

**2.4 Hash side: holds, with two caveats.** Grover gives a quadratic speed-up on preimage search; 256-bit outputs retain ~128-bit PQ preimage security and collision security that NIST treats as adequate at its Category 2. Caveat one: Poseidon's security argument is algebraic and its margin has been *classically* revised more than once; a PQ-first profile that also wants a conservative hash would select SHA-256 / BLAKE3 trees — which is what the Flock row offers and what `digestMultibase` already uses outside the circuit. Caveat two: nullifier and pseudonym constructions assume the holder *secret* has full entropy; a 128-bit uniformly random secret is fine, a secret derived from a low-entropy source is not, and Grover halves it.

**2.5 Fiat–Shamir and hash-based proof systems.** Transparent IOP-based systems (FRI/STARK, Ligero/Ligerito, Brakedown, WHIR, STIR, Binius) rest on hash collision resistance plus the random-oracle model, and Fiat–Shamir for the Kilian/Micali family has been proven sound in the *quantum* random-oracle model. "Plausibly post-quantum" is the honest label and the spec already uses it for Flock; it should use the same label for ProveKit's core and withhold it from any route that passes through a Groth16 wrapper. One further caveat belongs beside the label: the Reed–Solomon proximity-gap conjectures many FRI/STIR/WHIR parameter sets assumed were disproved in late 2025 and early 2026 (§6.2) — a parameter correction, not a break, but one that hits binary-field systems hardest, so a PQ profile must name the bound it relies on.

**2.6 Harvest-now exposure, by artefact.** Only artefacts whose *confidentiality* rests on a quantum-fragile assumption are exposed to harvest-now attacks. In this spec that is: encrypted transport (out of scope — the Trust Tasks envelope and VTI messaging keys, X25519, are a sibling spec's problem), and any correlation protection that rests on DDH rather than on a hash: the Tag_DDH pseudonyms of the PCS route are the one such case, since a harvested transcript of tags becomes linkable once DDH falls. Everything else in the ZKP spec is a *forgery* exposure, which is forward-looking only. This distinction belongs in Security Considerations item 8, which today says only "pairing-based constructions have no post-quantum path".

## 3. Design direction — fix the issuance contract, then the prover

The order follows swappability (LIV-ALG-01) and the 8 September call.

**3.1 Signatures over commitments, outside the circuit — the pattern to standardise.** The DTG constructions already assume issuers who can choose commitments ("issuer-chosen commitments", X3, record 010 issuance: "ZK-friendly signature *or published commitment*"). Take the second branch and make it the PQ branch: the issuer publishes a hash commitment (leaf) or a root and signs *that* with a PQ signature; the circuit proves hash-membership, commitment-opening and predicates and **never verifies a signature**; the verifier checks the PQ signature on the root in the clear. This is the set-root primitive cred-tf #40 already describes ("signed published root + zero-knowledge membership/status proof"). The note's contribution is to say that the published-root branch is the *only* branch that is PQ-ready at acceptable cost today: proving an ML-DSA or SLH-DSA verification *inside* a hash-based circuit is in the millions-of-constraints class (figures in §6), and a Falcon verification needs NTT gadgets no credential toolchain ships.

Consequence for records: every `signature-verify` clause gains a second realisation — "**root-signature-outside**: the clause is discharged by a verifier-side PQ signature check on the published root the membership clause proves against" — with the disclosure-set consequence that the root, not the credential, is what the verifier sees. For records 020/021 (delegation and attenuation chains) each hop's countersignature becomes each hop's *commitment* in a signed registry, which is a credential-specification change (§4.4).

**3.2 Which PQ signatures.** For root and leaf signing outside the circuit the choice is governed by issuer PKI, not by the circuit: **ML-DSA-65** (FIPS 204) as the default; **SLH-DSA** (FIPS 205) where a hash-only assumption set is wanted — registry roots are few and long-lived, so the large, slow SLH-DSA signature is affordable there and buys the most conservative assumption; **FN-DSA / Falcon** only once FIPS 206 exists — it has no public draft as of today (§6.3), so it cannot be written into a profile yet. Hybrid with Ed25519 during the overlap period as a Data Integrity *proof set*, in exactly the form VTI-KEY-103..105 already specify for attestation artefacts — the ZKP spec should **cite those requirements rather than restate them**.

**3.3 Holder binding without a curve key.** Record 004's relation is already `pk_presentation = PRF(secret, context)`; keep it and drop "EdDSA / Baby-Jubjub identity in-circuit" from the selected set. The presenter's *session* key for signing the transcript can be whatever the transport accepts, including ML-DSA; what the proof binds is the PRF image, which is hash-shaped. Record 007 (common control) is two Poseidon openings sharing a secret — PQ as it stands. The integration-chapter sentence "a SNARK-native key (BabyJubJub or BLS12-381 Multikey)" should become "a hash commitment to the holder secret, published beside the identifier's verification methods"; the did:key Ed25519 limitation it discusses is unchanged.

**3.4 Proof system.** Keep Groth16 as the measured benchmarking vehicle (the stack entry already says "not the task force's selection"), and make the *selected* construction for any profile that claims LIV-ALG-07 readiness a hash-based prover: Flock-class over SHA-256/BLAKE3 trees for the membership, non-revocation and transcript side; WHIR/Spartan (ProveKit core **without** the Groth16 wrapper) or a STARK where a Poseidon tree is retained. The cost is the one the spec already prints — ~700 B proofs become ~400–700 KB — and D3 ("a proof fits the transports DTG credentials already travel over") should be decided with that number rather than left "open". Trust Tasks already carries multi-megabyte payloads; a 0.5 MB proof is a profile question, not a blocker.

**3.5 The PCS route (records 023/024 option 1).** The Berkeley construction is the most elegant thing on the board and it is pairing-based end to end. The honest record is: *not on the PQ path*; the lattice literature has anonymous-credential and blind-signature analogues (§6.3) with proofs in the tens to hundreds of kilobytes and no production toolchain. Record 024 should carry a horizon line saying so, and option 3 (the lab's hash-based `vetting_attest`, k + 1 proofs) should be marked as the PQ-compatible realisation of the same statement once its prover is hash-based.

**3.6 What not to do.** Do not put a PQ signature verification inside the circuit to "keep the as-signed model" — the SIROS/Longfellow legacy-rails class (row L) is a different route for credentials DTG does not issue, and it inherits the issuer's curve. Do not treat a Groth16 wrapper around a STARK as PQ. Do not claim hash chaining restores anything after a signature break (LIV-ALG-08 already forbids it). Do not make PQ a blocker for the first implementable release (decision doc §24 stands) — make it the *selected* profile's horizon statement instead, so that V1 ships with an issuance contract that does not need re-issuing credentials to migrate.

## 4. Concrete changes to propose — each small enough to be one PR

Ordered by where it lands; none ratifies a construction choice, in keeping with the drafting rules.

**4.1 ZKP spec — a WG item (WG-18, "Discuss: post-quantum issuance contract").** Text for the body, next to WG-02 (issuance and witness contract): *"The task force selects, for the first conformant profile, between (a) issuer signatures a circuit verifies and (b) issuer signatures over published commitments a verifier checks outside the circuit. Only (b) has a post-quantum realisation at credential-presentation cost today. Required output: a decision on (b) as the profile default, a named PQ signature suite for roots (ML-DSA-65 or SLH-DSA), and the hybrid overlap rule, by reference to VTI-KEY-103..105."* Status: open; source: this note + the 8 September call.

**4.2 ZKP spec — split the `postQuantum` field in proving-system entries.** Today one string ("no — pairing-based", "plausibly post-quantum", "hash-based core — the wrapper is not"). Replace with two: `pqSoundness` and `pqZeroKnowledge`, each `holds | falls | plausible`, plus `pqNote`. Groth16 reads `falls / holds`; Flock `plausible / plausible`; ProveKit `plausible / plausible` for the core with a note that the Groth16 wrapper is `falls / holds`; Longfellow `plausible / plausible` for the proof with a note that the *statement* (ECDSA) falls. One schema change in `construction-record.schema.json`'s sibling stack schema, four stack-file edits, one render-lib column.

**4.3 ZKP spec — a `quantumHorizon` line per record, generated into Security Considerations item 8.** Each record's Horizon block already lists cryptoperiods. Add one structured field, `quantumHorizon: { forgery: [...], confidentiality: [...] }`, listing which clauses fall to forgery and which (if any) lose confidentiality. For most records: forgery = the `signature-verify` clause under a curve suite; confidentiality = none. For 024 option 1: forgery = credential and tag; confidentiality = the Tag_DDH pseudonym stream. Item 8 then regenerates as a per-record list instead of one sentence, which is how the privacy items 7+ are already produced.

**4.4 Credential specification — issue: "A post-quantum cryptosuite, or a hybrid proof set, for DTG credentials".** The spec names one cryptosuite (`eddsa-jcs-2022`) and cites one W3C cryptosuite document; it is the only one of the three sibling DTG specifications with no PQ text. Ask for: (i) the two quantum-resistant suites the Trust Tasks framework already pins (`mldsa44-jcs-2024`, `slhdsa128-jcs-2024`, from the W3C Quantum-Resistant Cryptosuites draft, §6.6) admitted for the credential `proof` on the same "draft; pinned" terms, so a credential and the task document that carries it can be signed under one suite set, (ii) the proof-set rule — cite VTI-KEY-102..105 verbatim rather than inventing a second rule in a second DTG spec, (iii) for VDC/VAC chains, a *committed* hop form so chain validity is provable without a signature inside the circuit (this is the same ask record 008/022 made for salted binders — the editor already took #38 and #58 in this spirit). File against dtgwg-cred-spec, attributed to the ZKP TF, linking WG-18.

**4.5 ZKP spec — decide D3 against the real number.** The ADR-001 crosswalk row D3 is "open — a profile decision; the options table shows both numbers". Propose: *"D3 is met for a profile whose transport carries ≥ 1 MB task payloads (Trust Tasks does); a proof ≤ 700 KB is within budget. The sub-kilobyte proof is not a V1 requirement."* This unblocks selecting a hash-based prover without re-opening ADR-001.

**4.6 Evidence repository — a PQ stack row that is measured, not conjectured.** The lab has three circom circuits and Flock is a Yukon lane this keeper already runs. The smallest honest step is record 001 (set membership, depth 20) re-expressed as a batch of BLAKE3 compressions and proved with Flock on the same lab machine, so the options table gets a `measured` PQ row beside the Groth16 one. Nothing else in the catalogue moves until that number exists; with it, D1/D3 are decided on evidence.

**4.7 Implementation guide (dtgwg-zkp-tf) — one chapter.** The guide's cryptographic background already has "Post-Quantum Status: pairing-based broken by Shor; hash-based quantum-resistant" as two bullets. Replace with a chapter that carries §2 of this note (soundness vs zero-knowledge, forgery vs confidentiality exposure, the signature as the non-swappable layer) and the issuance pattern of §3.1 with a diagram. This is the chapter other DTG task forces (cred, VTI, trust-tasks) can cite instead of each writing their own PQ paragraph.

**4.8 Liveness requirements v0.4 — one new requirement.** LIV-ALG-07 says V1 MAY be pre-quantum provided agility is preserved. Add **LIV-ALG-09 — Issuance separability**: *"A profile MUST state whether the issuer signature is verified inside the proof or over a published commitment outside it. A profile that verifies a pre-quantum signature inside the proof MUST state that its forgery horizon is the signature's, whatever the proof system's."* That closes the loophole where a PQ prover is advertised over a curve-signed credential.

None of these names ZKPs; all of them name the signatures DTG credentials carry today. A conformant V1 profile that is still issuing Ed25519-only credentials in 2030 is out of step with every one of them.

## 6. Figures and sources the note rests on

Compiled 2026-10-12; the full source list with confidence tags is in the companion file `RESEARCH-2026-10-12-pq-sources.md` beside this note. Items marked *self-reported* have no peer review and should be cited as such in any spec text.

**6.1 Soundness vs privacy (the §2 split), primary sources.** Groth16 soundness is argued in the generic bilinear group model (ePrint 2016/260). ETSI TR 119 476-1 §9.1: "a quantum adversary will be able to break the authenticity of QEAA systems but not (in most cases) their privacy … systems achieving unconditional privacy are immune to the store-now-decrypt-later attack"; §9.2 notes "harvest now, forge later" is a narrower window than harvest-now-decrypt-later; CFRG BBS draft-12 §6.9 names the same property "everlasting privacy". NIST IR 8547 §4.1.3 keeps ≥128-bit hashes at Category 1.

**6.2 Hash-based proof systems in the quantum random-oracle model.** Chiesa–Manohar–Spooner, ePrint 2019/834: IOP-based succinct arguments with round-by-round soundness are secure in the QROM. Chiesa–Ma–Spooner–Zhandry, ePrint 2021/334: Kilian's argument is PQ in the standard model from collapsing hashes. Block et al., ePrint 2023/1071: Fiat–Shamir security of FRI. **Caveat that belongs in any PQ profile:** the "up-to-capacity" Reed–Solomon proximity-gap conjectures that FRI/STIR/WHIR parameter sets often assumed were disproved between Nov 2025 and Apr 2026 (Diamond–Gruen ePrint 2025/2010; Crites–Stewart 2025/2046; Ben-Sasson et al. 2025/2055; Kambiré arXiv 2604.09724). Impact is parametric, not a break — a few percent under the restated conjecture, roughly 2× proof size under *proven* bounds — and binary-field systems (the Flock/Binius family) are the most exposed. A profile should name the bound it relies on. ProveKit/WHIR, Binius and Stwo have not published their re-parameterisation.

**6.3 PQ signatures and anonymous credentials.** FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA) final since Aug 2024; **FIPS 206 (FN-DSA/Falcon) still has no public draft** as of today — do not write Falcon into a profile. NIST additional-signature Round 3 (IR 8610, May 2026): FAEST, MAYO, MQOM, QR-UOV, SDitH, SNOVA, SQIsign, UOV (HAWK withdrawn Sep 2026). Lattice anonymous credentials exist at research grade: Argo et al. CCS 2024 (credentials ≈ 80 KB), Bootle–Lyubashevsky–Nguyen–Sorniotti CRYPTO 2023 (blind signatures, AC and group signatures from one framework), Beullens et al. 2023/077 (22 KB two-round blind signatures), all buildable in IBM's LaZer library (CCS 2024) over LNP22/LaBRADOR. ETSI §9.4.1: no standardisation effort exists for PQ blind signatures, group signatures or anonymous credentials. This is the honest horizon line for the PCS route (§3.5).

**6.4 Proving a PQ signature inside a circuit — why §3.1 keeps it out.** All *self-reported*: ML-DSA-87 verification ≈ 16.5 M R1CS constraints in circom; a Dilithium verifier in SP1 ≈ 22 s with NTT ≈ 50 % and SHAKE ≈ 18 % of cycles; analytic estimates put any ML-DSA verification in the millions of constraints because of degree-256 NTTs over a 23-bit non-native modulus. No credible in-circuit figures exist for SLH-DSA or standard Falcon. The one production system verifying a lattice signature natively inside a STARK (Polygon Miden, RPO-Falcon512) does so by replacing SHAKE with an algebraic hash — a non-standard variant, not FIPS. Compare the lab's whole membership circuit: 11,523 constraints.

**6.5 Proof sizes.** Groth16: 128 B (BN254) / 192 B (BLS12-381), constant; the lab's 721 B is the snarkjs encoding. Hash-based: WHIR ≈ 63 KiB per opening; ProveKit end-to-end ≈ 0.7–1 MB; zkVM STARK "shrink" stages 218–870 KiB (ePrint 2026/2383); Flock 2^18 BLAKE3 compressions ≈ 437 KB; LaBRADOR lattice 58 KB for 2^20 R1CS; zkDilithium tokens 85–175 KB. Every production stack that needs on-chain verification (SP1, RISC Zero, Stwo, ProveKit) wraps in Groth16 and loses PQ soundness at the wrapper — the spec's ProveKit entry already says so; the `pqSoundness` split of §4.2 makes it machine-readable.

**6.6 Standards hooks a credential spec can cite today.** RFC 9964 (ML-DSA in JOSE/COSE, 2026); RFC 9901 (SD-JWT, hash-based disclosures, algorithm-agile by construction, 2025); IETF LAMPS composite ML-DSA signatures draft-19 (RFC Editor queue, Oct 2026); W3C "Quantum-Resistant Cryptosuites v1.0" FPWD (16 Jun 2026: `mldsa44-jcs-2026`-style suites, `-sd-` variants, no hybrid, experimental); W3C VC WG charter 2026–2028 lists quantum-safe cryptosuites as a *tentative* deliverable only. For the credential-specification issue of §4.4, the ask is therefore a *slot* for a second cryptosuite and the proof-set rule by reference to VTI-KEY-102..105, not a named final suite.

**6.7 Longfellow, for the record.** Frigo–shelat (ePrint 2024/2010): the argument layer uses only SHA-256 and is PQ-plausible; the statement proven is an ECDSA signature, so credential soundness is classical. IETF 124 dispatch (Nov 2025) did not settle a venue; CFRG feedback from EU, Apple and Google asked for PQ-preferred schemes with device binding, which rules out the BBS family. Google donated the library to the PQCA (Sep 2026) — stewardship, not a PQ claim about the credential system.

## 7. What is still unknown — say so in the spec rather than guess

- No peer-reviewed in-circuit cost for any NIST PQ signature; the figures in §6.4 are self-reported.
- No agency document on PQ + ZKP for digital identity; ETSI TR 119 476-1 §9 is the nearest and it is informative.
- No PQ anonymous-credential standards track anywhere (IETF, W3C, DIF, ToIP). The TF would be first.
- FIPS 206 timing unknown.
- Proximity-gap re-parameterisation status of WHIR/ProveKit, Binius/Flock and Stwo unpublished — a measured Flock row (§4.6) should state which bound its parameters assume.
- Whether a hash commitment to the holder secret can live in a DID document as a verification-method-adjacent resource is a cred-spec / did:webvh question already open under record 007 / WG-14; the PQ reading changes nothing there except removing the BabyJubJub/BLS12-381 Multikey alternative.
