## Implementation Guide: From a Trust-Graph Outcome to a Proof

This section is informative. The explanatory treatment has moved to the [companion Implementation Guide](https://trustoverip.github.io/dtgwg-zkp-tf/). The guide and this extraction are coordinated drafts until their pull requests merge. Construction definitions and conformance remain in this specification.

> **WG-01 — Proposed for ratification: outcome and first milestone.** Use credential-bound private membership eligibility as the first implementation milestone supporting ADR-001, while retaining construction 010 as the flagship complete use case. Does the group accept this sequence and the stated distinction? Status: proposed; no decision recorded.

> **WG-02 — Discuss before implementation: issuance and witness contract.** Which credential format, issuer-signature route, holder-key capability and offline linkage artifact does the first profile support? Required output: a pinned input contract and an explicit list of unavailable or unsupported inputs. Status: unresolved technical dependency.

> **WG-18 — Discuss before implementation: post-quantum issuance contract.** WG-02's issuer-signature route decides this specification's post-quantum horizon, because the proof system is swappable by software and the credential signature is not. Two routes: (a) an issuer signature the circuit verifies; (b) an issuer signature over a published commitment or root, checked by the verifier outside the proof, with the proof covering hash membership, openings and predicates only. Only (b) has a post-quantum realisation at presentation cost today — an ML-DSA verification inside a circuit is in the millions of constraints (self-reported), against 11,523 for the lab's whole membership proof. Required output: (b) as the first profile's default, or a reasoned alternative; the post-quantum suite for roots and leaf commitments (ML-DSA-65, or SLH-DSA-128s for long-lived registry roots — the suites the Trust Tasks framework pins), stated as the profile's horizon rather than a V1 blocker; the hybrid overlap rule by reference to [DTG-VTI] VTI-KEY-103..105; and a decision on ADR-001's D3 against the measured proof size of a hash-based prover. Status: proposed 2026-10-12; no decision recorded. Source: Security Considerations item 8; the 8 September call (the credential signature scheme as the non-swappable choice).

> **WG-03 — Evidence request: construction choice.** Select a common workload and target device for comparing compatible routes. Request a reproducible result for the full statement, including credential authentication and status checks. Status: no backend recommendation adopted by this draft.

> **WG-04 — Proposed for ratification: result boundary.** Keep proof verification, policy acceptance and action completion distinct in the spec and implementation examples. Status: proposed wording; record the group's resolution and source discussion before treating it as adopted.
